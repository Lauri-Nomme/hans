# Code audit — 2026-08-28

Full-fidelity audit of the `hans` solution: `bb_archiver/` (core tool),
`tools/` (Rust accelerators), `corpus/` (validation gates), plus lab/config
hygiene. Method: full read of `bb_archiver/{scrape,model,emitter,jsonwriter,cli}.py`,
`tools/*/src/main.rs`, `corpus/{gate1,gate2,gate2b,gate3,capture}.py`,
cross-checked against `FORMAT_SPEC.md`, `README.md`, git history
(`8ced5f9`, `c8cfc2f`), and the corpus REST dumps. Findings include one
live reproduction against a synthetic scrape.

Overall verdict: architecture is sound (scrape -> assemble -> validate;
gates validated against a golden admin export; O(1)-memory streaming in
`assemble`; good model caching; batched merge-base with dedupe; Rust
object-tar with a strictly interleaved `cat-file` protocol; gate3 client is
rate-limit-aware, ETag-caching, resumable). The findings below are ordered
by severity.

---

## Bugs (correctness)

### 1. Silent user misattribution — worst finding (proven by repro)

`bb_archiver/model.py:113-114`:

```python
def _slug_key(self, slug):
    return slug if slug in self.users else next(iter(self.users.keys()))
```

Any slug not present in `self.users` is silently replaced by the
alphabetically-first harvested user. The archive then attributes that
person's identity to someone else — a data-corruption class bug, and it is
silent (no warning, no failure).

Reachable because `harvest_users()` (`model.py:96-104`) only harvests:
PR author, `reviewers`, `participants`, per-activity `user`, and the
*top-level* activity comment author. It misses:

- `addedReviewers` / `removedReviewers` inside `UPDATED` activities —
  consumed by `emitter.py:268-271`. A reviewer added and then removed
  before the scrape appears *only* there. The fixture itself exercises
  this shape (`grace` added then removed in `pr_1`/`pr_6` activities); it
  hides in the fixture only because `grace` is a reviewer elsewhere.
- nested reply authors — `_comment()` (`emitter.py:200-201`) recurses into
  `comment.comments` and calls `ref_id_for` per reply author, but only the
  top-level comment author is harvested. A replier who is not also a
  participant/reviewer/author is misattributed.
- task `resolver` (`emitter.py:208`) — resolvers are not harvested.
- comment editors (the `modified` path in `_comment_events`,
  `emitter.py:228-235`).

Reproduction (synthetic scrape dir; `zoe` appears only as an added
reviewer):

```
harvested users: ['alice', 'bob']
ref_id_for('zoe') -> alice|Alice||NORMAL
```

Expected: `zoe|Zoe||NORMAL` (or a hard error / synthesized identity), not
Alice.

Fix: harvest from the missed fields as well, and make `ref_id_for` warn
(or raise, or synthesize a deterministic `slug|slug||NORMAL` stub) on
unknown slugs instead of silently substituting.

### 2. Non-retryable HTTP errors are retried and masked

`bb_archiver/scrape.py:94-118` (`Api.get`): for any status not in
`(429, 500, 502, 503, 504)` — e.g. 404, 401 — the code calls
`r.raise_for_status()`, which raises `HTTPError`, a subclass of
`requests.RequestException`, which the `except` clause catches. Result:
4 pointless retries with exponential sleeps, then a generic
`RuntimeError("gave up after N retries: <path>")` that hides the actual
HTTP status. A 401 (bad credentials) or 404 (wrong repo) costs ~1 minute
of sleeps before failing with an uninformative message.

Fix: re-raise immediately for non-retryable statuses (or at minimum do not
catch `HTTPError`), and include the status code in the final error.

Note: `corpus/gate3.py` handles this correctly (it re-raises outside the
retry loop for non-retryable codes); `scrape.py` should match.

### 3. gate2 `check_refs` hardcodes `FIX`/`golden`

`corpus/gate2.py:143-144`:

```python
ra = load(A, f"{kind}_{'FIX'}_golden")
rb = load(B, f"{kind}_{'FIX'}_golden")
```

This ignores `_proj_repo()` (which the same file implements for the PR
checks). The README's documented production flow
(`python3 corpus/gate2.py ./scrape/SX ./scrape/sx-lab-b`, described as
"PR-count-agnostic ... built for 10k PRs / 863k objects") therefore
reports `branches: missing on one side` + `tags: missing on one side` and
fails spuriously for any repo other than FIX/golden.

Fix: use `_proj_repo(d)` per side, as `pr_ids` already does.

### 4. gate3 `_norm_refs` is stale vs the current scraper

`corpus/gate3.py:178-189` filters out `refs/remotes/*`,
`refs/pull-requests/*`, and peeled `^{}` refs — but not
`refs/stash-refs/*` or `refs/keep/*`. Since commit `c8cfc2f` ("scrape:
stash refs must be written as refs/stash-refs/... in the mirror") the
mirror carries `refs/stash-refs/pull-requests/<id>/from` for every PR (and
`refs/keep/<sha>` for unwritable refnames), so every rerun of gate 3
reports `refs only in BB: [...]` and fails spuriously. Gate 3's PASS
predates that commit; the gate and scraper have drifted apart.

Fix: filter `refs/stash-refs/` and `refs/keep/` in `_norm_refs` (they are
mirror-internal retention refs, not content refs), then re-run gate 3.

### 5. Emitter hardcodes HEAD to `refs/heads/main`

`bb_archiver/emitter.py:453`:

```python
entries = {"HEAD": b"ref: refs/heads/main\n", ...}
```

FORMAT_SPEC.md:403 documents `HEAD = ref: refs/heads/main` — but that is
an observation of the golden repo (whose default branch is `main`), not a
format invariant. Any repo whose default branch is not `main` gets an
archive whose HEAD dangles, diverging from a real admin export (which
writes the actual default branch). The fix is trivially available: the
branches REST dump already carries `isDefault: true` (verified in
`corpus/rest/branches_FIX_golden.json`), and `scrape.py` already fetches
branches.

Also missing from README's "Known fidelity gaps" list, so users won't
expect it.

### 6. gate1 cannot fail on unclassified diffs (refs/caches)

`corpus/gate1.py:83-98`: only `*.json.atl.gz` (semantic JSON) and
`*.tar` (object maps) are genuinely compared. A byte difference in
`metadata.atl.tar.atl.gz` (refs, reflogs — i.e. wrong refs or wrong
reflogs) or `caches.atl.tar.atl.gz` (wrong merge-base caches) falls into
the `else` branch and produces only a *note*:

```
{name}: raw byte diff (unclassified)
```

Notes never fail the gate. Gate 1 is the golden-master check; a wrong ref
or wrong `cached-ancestor.txt` would PASS it. (Gate 2/2B would likely
catch functional breakage downstream, but the golden gate's job is exactly
this.)

Fix: fail (or at least classify + compare inner tar entries) for every
unclassified member; `caches.atl.tar.atl.gz` and `metadata.atl.tar.atl.gz`
are cheap to compare entry-wise like the objects tar.

## Inefficiencies

### 8. gate2 loads every object's full content into RAM for a guarantee
### available far more cheaply

`corpus/gate2.py:163-192` (`_git_objects`) builds `{sha: (type, raw
bytes)}` for both mirrors by streaming `git cat-file --batch`, then
`check_git_objects` diffs contents (`ma[sha] != mb[sha]`).

Precision on what the content diff actually buys (initially overstated in
this audit as "zero information"; corrected after a live test):

- **For migration fidelity, the SHA+type sets alone are sufficient.** Git
  object SHAs are content hashes, so equal sets imply equal contents.
  Nothing about the *round trip* is learned from the byte compare.
- **The content diff does have one real function: on-disk integrity of
  the two mirror inputs.** Git re-verifies object hashes only at *ingest*
  (fetch -> index-pack / unpack-objects). Plain reads do NOT re-hash:
  verified live — a loose object whose zlib stream still decompresses but
  whose bytes differ from its path-hash is served by `git cat-file` with
  return code 0 and no complaint. So post-ingest corruption (bit rot, a
  bad `repack` write, manual tampering) would be served silently to
  gate2, invisible to the SHA-set compare but caught by the byte diff.
  Only `git fsck` (hash-path mismatch) catches this class.

So the compare is not useless — but the same guarantee is available
streaming, with O(1) RAM: `git fsck --no-dangling --no-progress` on both
mirrors, or `git cat-file --batch-check` + fsck-style re-hash. Holding
`{sha: raw bytes}` for both sides is the GBs-scale cost at the advertised
863k objects.

`corpus/gate3.py` does the migration-fidelity part correctly:
`verify_git_objects` compares SHA sets + types only, via
`--batch-check`, no content transfer.

Fix: keep the SHA+type set compare; replace the in-RAM content diff with
`git fsck` on both mirrors (or make the content verify opt-in for small
repos).

### 9. `validate` buffers the entire `objects.atl.tar` although only
### member names are needed

`bb_archiver/cli.py:115-117` — `_check_ref_object_integrity` does
`repos[rid]["objs"] = f.read()` on the inner objects tar, and `_inner_map`
then reads every member body (`t.extractfile(m).read()`), only to throw
the bodies away: the check consumes nothing but member *names* —

```python
objs = {n.replace("/", "") for n in _inner_map(r["objs"])}   # cli.py:123
for refname, content in _inner_map(r["meta"]).items():       # meta: bodies used, tiny
```

So at production scale the validate step holds the repo's entire object
content in RAM (twice over: outer member buffer + inner member map) to
compute a set of ~30 MB of names.

The bodies are genuinely skippable, and no temp file is needed: the outer
archive is opened on a real seekable file, so `archive.extractfile(name)`
returns a seekable `_FileInFile` that can be handed straight to
`tarfile.open(fileobj=..., mode="r")`; walking `getmembers()` then reads
only headers and *seeks* past data blocks (verified — no body bytes are
read). Memory stays O(1):

```python
with tarfile.open(fileobj=archive.extractfile(name), mode="r") as it:
    objs = {m.name.replace("/", "") for m in it.getmembers()}
```

(The `meta` inner map at cli.py:124 is fine as-is: it needs the ref-file
contents and is small.)

### 10. Checkpoint rewrite is O(n^2) in PR count

`bb_archiver/scrape.py:197-199` — after every PR:

```python
done.add(pid)
ckpt_path.write_text(json.dumps({"prs_done": sorted(done)}))
```

Each write re-sorts the whole growing set and re-serializes all ids: at
10k PRs that is ~50M comparisons and hundreds of MB of redundant writes
(10k files-rewrites averaging ~40 KB). An append-only JSONL
(one id per line, loaded once at start) or batching every N PRs removes
the quadratic behavior entirely.

### 11. Minor inefficiencies

- `corpus/gate1.py:198-204` — `_compare_activities` multiset match is
  O(n^2) (`for i in rb: for j in sb:` with a `used` bitmap). Fine for the
  7-PR golden; will not scale if reused for production repos. Sort
  signatures and two-pointer match instead.
- `bb_archiver/emitter.py:312-333` (`pr_cache`) — when
  `_merge_bases` already returned `None` for a pair (disjoint histories,
  or no git dir), `pr_cache` re-runs a single-PR `git merge-base`
  subprocess (`_merge_base`) that will deterministically fail again, then
  falls back to `fromTip`. Harmless but redundant; pass the
  already-computed result through.
- `bb_archiver/emitter.py:353-356` — `_merge_bases_rust` imports
  `as_completed` and `threading`; both unused.
- `tools/bb-obj-tar/src/main.rs:184` — usage string advertises
  `[--jobs M]` but the arg parser exits 2 on any unknown arg; `--jobs` is
  not implemented. Same for `tools/bb-merge-base/src/main.rs:14`
  (`[--nargs]`).
- `corpus/gate3.py:103-119` — the ETag cache is keyed by `path` only,
  while the request URL includes params; `paginate` reuses one `path`
  across pages, so cached ETags for page 1 are replayed against page 2+
  (GitHub re-evaluates per full URL, so no wrong data — just useless
  conditional requests). Key the cache by full URL.
- `corpus/capture.py:92-96` — the PR list fetch is a single
  `limit: 100` GET with no pagination loop (fine for the 7-PR fixture;
  would silently truncate on a bigger repo).

## Design / robustness

### 12. `bb-obj-tar` trusts `packs[0]` from an unordered `read_dir`

`tools/bb-obj-tar/src/main.rs:213-228` — after `repack -adf` there is
normally exactly one pack, so the fast path is fine in the emitter's
flow. But:

- `read_dir` order is unspecified; if a second idx ever coexists (a
  `.keep`ed older pack survives `repack -ad`, crash debris, a cruft
  pack), the tool may pick the wrong/incomplete pack and silently emit a
  partial object tar.
- An empty repo (zero commits) produces no pack at all -> exit 1 ->
  `Emitter.git_objects` raises `RuntimeError("bb-obj-tar failed")`, so
  `assemble` crashes on a repo with no commits. (The pure-Python path
  fails the same way via "no pack produced by repack".)

Suggested: refuse when `packs.len() > 1` (or verify the chosen pack's
object count against `git cat-file --batch-all-objects --batch-check`
count), and emit an empty tar (1024 zero bytes) for a zero-object repo.

### 13. Every harvested user becomes PROJECT_ADMIN

`bb_archiver/emitter.py:96-102` — `project_permissions()` grants
`PROJECT_ADMIN` to every user in `self.m.users`. This matches the golden
export and FORMAT_SPEC.md:151-156 (where the lab admin export carried
exactly that), and permissions are a declared non-goal — but it is a
deliberate fabrication with a real-world side effect: importing this
archive into a *live* Bitbucket instance grants project admin to every
scraped user. Worth a line in README's "Known fidelity gaps" so nobody
learns it the hard way.

### 14. Small surprises

- `--mtime 0` means "now", not epoch: `cli.py:184` defaults `--mtime` to 0
  and `emitter.py:49` does `int(export_mtime or time.time())` — falsy 0
  falls back to wall-clock. Surprising for the documented
  byte-reproducibility use case; use `None` as the sentinel.
- `index.json` `prs` and `entities` are incomplete after a resumed scrape
  (`scrape.py:196`, `scrape.py:151`): on resume the index starts fresh and
  only records that run's work. Nothing consumes these fields today
  (`grep` confirms gates read the `rest/*.json` dumps instead), but the
  file is documented as "ids + entity manifest", which it no longer is
  after a resume.
- `scrape.py:301` (`_valid_refname`) duplicates several checks the `bad`
  regex already covers (`..`, leading `.`/`~^:?*[`, etc.) — harmless
  redundancy, but one place to maintain.
- `Api._throttle` headroom is a fixed 10 with no config surface; fine,
  but worth exposing if production runs hit per-window budgets.
